# Однократный тихий перенос SaleBot → Chatwoot

Запускать из корня форка через `rails runner` в серверном Rails-контейнере.
Аккаунт фиксирован: **1**. Скрипт читает локальные файлы; SaleBot API и URL вложений
не запрашиваются. Ни токенов, ни изменений каналов в скрипте нет.

## Формат и принятые решения

- `--clients`: UTF-8 JSONL, одна строка `{"client": {...}, "messages": [...]}`.
  Поддерживаются только числовые `client_type`: `1` (Telegram) и `20` (MAX).
  Telegram `platform_id` должен состоять из цифр; ошибочные записи попадают в mapping
  с причиной. Клиент без сообщений переносится без создания беседы.
- `--report`: CSV UTF-8, допускается BOM, разделитель `;`. Обязательные колонки:
  `ID`, `Имя`, `Мессенджер`, `Тег`, `Заполненная заявка`, `Успех`, `Состояние воронки`.
  Дополнительные колонки разрешены. ID сопоставляется с `client.id`; дубликат ID,
  отсутствующая строка или колонка останавливают импорт вместо потери атрибутов.
- Время **без смещения трактуется как Europe/Moscow (UTC+03:00)** независимо от
  `Time.zone` Rails и TZ контейнера. Например, `2026-10-14 03:29:26.837000`
  соответствует `2026-10-14T00:29:26.837000Z`. Явное смещение в строке учитывается.
  Решение основано на описании выгрузки в карточке: настоящие серверные файлы
  исполнителю недоступны, сверить их с интерфейсом SaleBot локально не удалось.
  **Перед apply сопоставить хотя бы одно известное сообщение в SaleBot и dry-run**;
  если время в выгрузке UTC, требуется поправить `TIME_ZONE` и повторить проверку.
  `content_attributes.external_created_at` хранит ISO 8601 со смещением и микросекундами.
  Ограничение «переписка с 14.10» задаётся окончательной выгрузкой: скрипт переносит
  все переданные сообщения, сам дату не отсекает.
- Входящее сообщение отправлено контактом. Исходящее — пользователем **этого аккаунта**,
  если совпал `manager_email` без учёта регистра; иначе отправитель `nil` (бот/неизвестный
  менеджер). `manager_id` не используется, фиктивные пользователи не создаются.
- Текст сохраняется; `processed_message_content` равен итоговому тексту, как в штатном
  импортёре. Вложения `null`, одиночный объект или массив объектов превращаются в строки
  `Вложение: <attachment_url>` после текста. Загрузка файлов и аватаров отсутствует.
- В custom attributes контакта сохраняются `salebot_client_id` (строка), `salebot_tag`,
  `salebot_funnel_state`, `salebot_success`, `salebot_application`, `salebot_messenger`.
  Значения CSV сохраняются строками, без догадок о boolean. Тег CSV имеет приоритет,
  при пустом значении используется `client.tag`. Чужие ключи и имя существующего контакта
  сохраняются. Только новым контактам добавляется `salebot_import_created=true`.
- Метки: `salebot-funnel-<этап>` и `salebot-tag-<тег>`: нижний регистр, Unicode-буквы,
  цифры, `_`, `-`; остальные последовательности заменяются дефисом, крайние дефисы
  убираются. Например, `Заполненная заявка` → `salebot-funnel-заполненная-заявка`.
  Полностью непригодные значения пропускаются с причиной в stdout; исходное значение
  остаётся в custom attributes. Одинаковые после нормализации значения дают одну метку.
  Контакт и беседа получают обе метки с сохранением существующих.

## Почему импорт тихий и повторяемый

`Contact`, `ContactInbox`, `Conversation`, `Message`, `Label`, `Tag`, `Tagging` создаются
через `insert_all!`; изменения — через `update_columns`. `create!`, MessageBuilder,
`update_labels`, загрузка аватаров и callbacks не используются. Поэтому не создаются
SendReplyJob, уведомления, webhooks, события и задания автоматизации. Числовые enum
берутся из моделей. Счётчик `tags.taggings_count` в форке отключён; `cached_label_list`
беседы заполняется вручную. Кеш меток обновляется напрямую через существующий Redis helper,
без события `account.cache_invalidated`; операторам нужно перезагрузить вкладку.

Контакт сначала ищется по `(inbox_id, source_id)`, затем по `salebot_client_id` внутри
аккаунта 1. Telegram source_id — исходный цифровой ID; MAX — `max:<user id>`.
Telegram `social_telegram_user_id` записывается в `Contact.additional_attributes`;
у ContactInbox такого поля нет. Для нового ContactInbox явно создаётся pubsub_token.

История добавляется в последнюю беседу ContactInbox. Если её нет, создаётся resolved-беседа
с датой первого сообщения; Telegram `additional_attributes.chat_id` — числовой platform_id.
Существующие status, assignee и даты создания не меняются.
Беседа получает `salebot_imported=true`, `salebot_client_id`; только новая также
`salebot_import_created=true`. `last_activity_at` берётся из последнего сообщения всей
беседы, включая новые живые сообщения. Старые записи не должны сдвинуть активность назад.

Каждое сообщение имеет `source_id=salebot:<message.id>`, `status=sent`, `private=false`.
Непустой source_id дополнительно блокирует обычную исходящую Telegram-отправку.
Дедупликация проверяет все беседы ContactInbox: повторный импорт после появления новой
живой беседы не копирует уже перенесённую историю. Новые сообщения выгрузки поступят
в последнюю беседу. Одинаковые ID в самой выгрузке также не дублируются.
Не запускать два импортёра одновременно: source_id сообщений не имеет уникального индекса.

Dry-run по умолчанию выполняет только чтение БД и расчёт записей в памяти: ни INSERT/UPDATE,
ни расходования последовательностей ID, ни изменения Redis. Создаваемые ID в mapping пустые;
для найденных записей указаны настоящие ID. Все счётчики в этом режиме — планируемые.

## Переключение

1. Согласовать окно переключения. Зафиксировать счётчики текущего Chatwoot и сделать
   резервную копию PostgreSQL. Сохранить окончательные JSONL/CSV root-only за пределами
   репозитория, например `/srv/import/salebot/`; это персональные данные.
2. Остановить ответы и сценарии старого SaleBot, сделать **окончательную выгрузку**
   всех 4153 карточек и сообщений с 14.10. Проверить границу выгрузки, часовой пояс,
   распределение Telegram/MAX. В окне до подключения Chatwoot входящие сообщения
   должны оставаться в очереди провайдера; не очищать pending updates. Если SaleBot
   продолжал принимать сообщения после выгрузки, нужна дополнительная выгрузка.
3. Подготовить целевые inbox аккаунта 1: Telegram — штатный `Channel::Telegram`, MAX —
   `Channel::Api`. Создание Telegram-канала само настраивает webhook: до этого момента
   старый SaleBot должен быть остановлен, чтобы он не перехватил webhook обратно.
   Для предварительной проверки можно подготовить inbox с временным Telegram-ботом,
   а токен заменить на старый в согласованный момент. Токены не передавать импортёру.
   На время переноса приостановить обработку каналов/Sidekiq и работу операторов;
   создание записей канала и само переключение webhook — отдельные от импорта операции.
4. Выполнить dry-run, сначала при необходимости с `--limit 10`, затем без лимита:

   ```sh
   bundle exec rails runner deploy/evirma/salebot/import.rb -- \
     --clients /srv/import/salebot/clients.jsonl \
     --report /srv/import/salebot/report.csv \
     --telegram-inbox 12 --max-inbox 13 \
     --mapping-out /srv/import/salebot/mapping-dry.csv --dry-run
   ```

   Без `--apply` запись в БД запрещена; явный `--dry-run` необязателен.
   Проверить totals и все строки `status=skipped`, в том числе два ожидаемых
   нецифровых Telegram ID. Число входных клиентов должно равняться
   `clients_processed + clients_skipped`. Параметры одновременно `--apply --dry-run`
   запрещены; `--limit` — положительное число строк JSONL, включая пропущенные.

5. Выполнить ту же команду с **новым mapping-файлом** и `--apply` вместо `--dry-run`.
   Существующий mapping никогда не перезаписывается. stdout также сохранить в root-only
   журнал: по одному JSON-результату на клиента и итоговая JSON-строка `totals`.
   Запись идёт транзакциями по 200 клиентов. Ошибка откатывает текущую пачку;
   предыдущие пачки уже зафиксированы и записаны в mapping. После исправления входных
   данных повторить весь запуск с новым mapping. Повтор разрешён и после успешного apply.
6. Проверить UI и БД по списку ниже. Передать бэкенду Evirma **apply-mapping**, отобрав
   MAX-строки `client_type=20`, `status=imported`: `max_user_id`, `chatwoot_contact_id`,
   `chatwoot_conversation_id` предназначены для `support.max_contact`. У карточек
   без переписки conversation ID пустой: не превращать его в `0` или строку `null`.
   Скрипт сам таблицу Evirma не обновляет. Остальные колонки: `salebot_client_id`,
   `client_type`, `contact_id`, `conversation_id`, `messages_inserted`, `messages_skipped`,
   `status`, `reason`, `contact_action`, `conversation_action`.
7. Подключить старый `@EvirmaSupportManager_bot` его токеном к целевому Telegram inbox,
   если ещё использовался временный. Проверить webhook; убедиться, что SaleBot его больше
   не меняет. MAX-соединитель переключить на старого MAX-бота и целевой API inbox:
   поиск связи обязан использовать `max:<MAX user id>`. Возобновить обработчики и операторов.
   Первое настоящее входящее должно попасть в существующий контакт в обоих каналах.

## Что проверить

- Из 4153 входных карточек сходятся созданные, найденные и пропущенные; нет необъяснимых
  пропусков. В mapping правильные ID обоих каналов и пустые conversation ID без сообщений.
- У Telegram и MAX по одной связи с правильным source_id. Порядок, направления и московское
  время истории правильные; исходящие неизвестного менеджера не подписаны чужим оператором.
- У контакта и беседы видны метки этапа и тега; существующие метки не потеряны. После
  обновления вкладки новые метки доступны в списке аккаунта.
- Вложения показаны ссылками в тексте, аватары не скачивались; новые беседы закрыты.
- Нет новых уведомлений, исходящих сообщений у клиентов, запусков автоматизаций и webhook
  для импортированных данных. Не принимать настоящие сообщения в проверяемом окне.
- Повторный apply с новым mapping: `messages_inserted=0`, число контактов, связей, бесед
  и меток не растёт. Убедиться, что последующий реальный ответ идёт через нужного бота.
- Импортированные исходящие Telegram нельзя редактировать/удалять через UI: существующий
  механизм синхронизации воспримет `salebot:*` как Telegram message_id и вызовет Telegram API.
  Для удаления истории использовать только описанный ниже тихий откат.

## Откат

Полный возврат **до возобновления трафика** — восстановить резервную копию БД, сделанную
перед импортом. Она также возвращает исходные custom attributes и метки существовавших
контактов/бесед. Нельзя восстанавливать всю копию поверх уже поступивших новых обращений.

Для выборочного удаления **только импортированных сообщений**, включая частичный неудачный
запуск, сохранить код ниже в `/srv/import/salebot/rollback-history.rb`. Он ограничен аккаунтом 1
и контактами с `salebot_client_id`, использует только `delete_all`/`update_columns`.
По умолчанию и с `--dry-run` он только показывает объём удаления. После остановки обработки
входящих применить явным `--apply`:

```sh
bundle exec rails runner /srv/import/salebot/rollback-history.rb -- --dry-run
bundle exec rails runner /srv/import/salebot/rollback-history.rb -- --apply
```

```ruby
args = ARGV.dup
args.shift if args.first == '--'
raise 'Use --dry-run OR --apply' unless [[], ['--dry-run'], ['--apply']].include?(args)
apply = args == ['--apply']
account = Account.find(1)
contacts = account.contacts.where("custom_attributes ? 'salebot_client_id'")
conversations = account.conversations.where(contact_id: contacts.select(:id))
messages = account.messages.where(conversation_id: conversations.select(:id)).where('source_id LIKE ?', 'salebot:%')
puts({ mode: apply ? 'apply' : 'dry-run', contacts: contacts.count, messages_to_delete: messages.count }.to_json)
if apply
  ApplicationRecord.transaction do
    ids = messages.reorder(nil).distinct.pluck(:conversation_id)
    messages.delete_all
    account.conversations.where(id: ids).find_each do |conversation|
      latest = conversation.messages.reorder(created_at: :desc, id: :desc).pick(:created_at)
      conversation.update_columns(last_activity_at: latest || conversation.created_at)
    end
  end
end
```

Этот выборочный откат намеренно оставляет контакты, связи, пустые беседы, метки и custom
attributes: они могли существовать до импорта или уже получить живые данные. Для их
ручной уборки отбирать только `custom_attributes.salebot_import_created=true` и сверяться
с apply-mapping (`contact_action`/`conversation_action=created`), резервной копией и новыми
связями/заметками/сообщениями. **Не удалять все контакты по одному salebot_client_id**:
этим атрибутом помечаются также переиспользованные контакты. Удаление через `destroy!`,
UI или фоновые задания для тихого отката не подходит. Полный точный откат атрибутов
существовавших записей возможен из сохранённой резервной копии.

## Проверки кода

```sh
ruby -c deploy/evirma/salebot/import.rb
ruby -c spec/evirma/evirma_salebot_import_spec.rb
eval "$(rbenv init -)"
bundle exec rspec spec/evirma/evirma_salebot_import_spec.rb
```

RSpec использует четыре синтетические карточки в `fixtures/`: Telegram с объектом/массивом
вложений, MAX, MAX без переписки, невалидный Telegram ID. Проверяются тишина, dry-run без SQL
записей, повторный запуск, новый живой разговор, существующие связи и сохранение бизнес-данных.
Проект требует Ruby 3.4.4; на машине исполнителя доступен только Ruby 2.6.10 без rbenv.
RSpec должен прогнать координатор в `evirma-chatwoot-rails-1` с текущими файлами ветки.
